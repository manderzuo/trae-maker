# Core 按 Key 真实积分结算与管理界面设计

日期：2026-09-23
状态：设计稿，待用户审阅
范围：Core ↔ AI Work 逐请求真实扣费回执、统一积分分配、API Key 管理界面与稳定后的测试数据清理切换。

## 1. 目标

确保每一笔 Core 请求都能以唯一请求编号关联到发起请求的 API Key，并依据 AI Work/上游提供的、可核验的实际积分回执结算。不同 Key 的请求、预占和余额严格隔离；并发下不得重复承诺积分，也不得用 Token、固定 1 积分或全局余额前后差额推算单次费用。

同时将 Core 的额度展示统一为上游 AI Work 可用积分，并重构 Key 管理，使管理员可以直接创建、分配额度、复制和管理 Key。改造稳定验收后，切换到干净的 Core 生产数据集并重新生成所有客户端 Key；当前测试数据在切换前保留，不提前删除。

## 2. 已确认的产品决策

1. Core 在受理请求时生成唯一 `request_id`，并在 Core 数据库中绑定用户、Key、额度预占和请求状态。AI Work 回执只需返回该请求编号，Core 不接受回执声称的 Key 身份。
2. 所有实际扣费以 AI Work 的逐请求真实积分回执为准。没有回执或回执无法核验时，不猜扣、不按固定值或 Token 量扣，保持预占并进入待对账。
3. 使用方案 A：调用前按可信的单次最高扣费额预占；结算时按真实费用入账并释放未使用预占；未知结果不得自动重试或释放预占。
4. AI Work 持久化逐请求计费记录。Core 可使用同步回执，也可按 `request_id` 查询最终回执，以覆盖流式输出、视频异步任务、断连和重启恢复。
5. 文字与视频共用一套 Core 积分额度。上游能力仍由 AI Work 判断；Core 不把 Token、每日 Token 或每日请求数作为积分计算方法。
6. AI Work 上游当前总可用积分是分配总量上限。额度不足或快照不可用时，不新增分配；若上游余额低于所有 Key 未用额度之和，显示缺口并暂停新的付费请求，不静默改写 Key 余额。
7. Key 界面沿用 AI Work 风格的管理列表，支持随时复制、分配额度、调整并发、启停和查询使用情况；Key 明文加密保存。旧测试 Key 和历史账务在最终干净切换中不迁移。
8. 概览页与 Key 管理页分开。概览图只统计已核验的实际积分消耗；待结算预占独立显示，不混入已消耗曲线。界面不显示活跃账号数。
9. 新环境稳定切换时，丢弃 Core 测试用户、普通 API Key、额度和请求账本、视频任务及统计，不迁移旧 Key，全部重新签发。保留 Core 管理员账户、AI Work 上游账户/凭据/真实积分和生成的素材/视频文件；新环境切换时轮换 Core—AI Work 桥接密钥并更新两端。切换前不删除任何现有数据。

## 3. 现状与证据

- Core 普通文字路径在成功后调用 `Settlement::Commit { actual_amount: Some(1) }`，因此成功请求目前不是按上游真实费用结算：`starlink-dimension-router/src/user_routes.rs`。
- Core 桥接客户端已生成并发送 `x-core-request-id`：`starlink-dimension-router/src/bridge_client.rs`。请求编号传递是已有基础，但并不代表实际扣费回执链路已经完成。
- AI Work 侧当前代码会读取 `x-aiwork-core-actual-amount`，但仓库内尚未发现负责从上游单次账单生成该回执的完整生产者；聚合余额接口不能归因到并发的单个请求。
- 现有视频计费设计已规定：受理不代表结算；无任务级费用证据时保持待对账；未知结果不自动重试。本文把同一原则扩展到普通文字与流式请求，并将额度来源调整为 AI Work 当前可用总额。
- 当前工作区里已有其他未提交/未跟踪的设计文件。本文只新增自己的规格文件，不覆盖或提交那些文件。

## 4. 系统边界

### Core

- 负责外部 API Key 认证、scope、Key 并发和余额校验。
- 生成请求编号并建立不可变的 `request_id → key_id` 关系。
- 负责原子预占、逐 Key 结算、释放预占、幂等和对账状态。
- 读取 AI Work 的统一上游余额快照用于概览和分配上限；绝不使用余额差作为单次扣费。
- 管理 Key 的额度、密文、状态、权限和审计记录。

### AI Work 桥接层

- 只接受经 Core 桥接鉴权、带有 Core 生成请求编号的内部请求。
- 在转发上游前持久记录请求编号、模型/能力、上游任务引用与计费状态。
- 从上游明确的请求级/任务级计费记录中取得实际积分，而不是从 Token、时长、货币成本或聚合余额差估算。
- 提供最终回执查询；同步请求可随桥接响应返回回执，流式和异步视频通过持久查询补齐。

### 数据隔离原则

AI Work 只需要知道请求编号，不需要知道 Core 用户或 Key ID。Core 始终用本地不可变映射确定应扣哪个 Key；任何客户端传入的请求编号或 Key 标识都不能覆盖该映射。

## 5. 请求与结算协议

### 5.1 回执字段

内部回执至少包含：

```json
{
  "request_id": "Core-generated-id",
  "status": "pending | final | unknown | unverified",
  "actual_credits": "0.000000",
  "unit": "credits",
  "source_ref": "upstream request or task reference",
  "task_ref": "optional video task reference",
  "observed_at": "RFC3339 timestamp"
}
```

只有 `status=final`、编号匹配、单位明确、来源可核验且金额精度受支持的回执才可结算。回执不得包含上游凭据、账号秘密或完整提示词。重复查询同一最终记录必须返回同一金额；同一请求出现冲突金额时进入待对账，不二次入账。

回执使用经 Core 配置的桥接鉴权通道传输。Core 以数据库中的 `request_id → key_id` 关系确定扣费对象，不信任回执里的 Key 字段，也不把内部计费头透传给普通 API 客户端。

### 5.2 单次费用上界与预占

1. Core 创建请求编号，并取得 AI Work 对本次请求的可信最高费用上界/报价；报价必须保证是上界，而非 Token 估算或普通预测值。
2. Core 在数据库事务中检查 Key 可用余额、Key 并发和统一上游余量，原子创建预占。
3. 预占成功后才向 AI Work 提交实际请求；AI Work 持久化关联后再转发上游。
4. 如果 AI Work 无法提供可信上界，不发起普通付费请求，不以固定额度替代。

额度使用定点十进制，内部以微积分（`1 credit = 1,000,000 microcredits`）存储，接口使用十进制字符串。超过六位小数或不能准确解析的回执不四舍五入，进入待对账。

### 5.3 生命周期

```text
Core 认证 Key / 绑定 request_id
    → 取得可信费用上界
    → 原子预占
    → AI Work 持久记录并调用上游
    → 同步回执或按 request_id 查询
    → Core 原子实扣 / 释放余量
```

- 上游明确拒绝且能证明未产生扣费：释放预占，标记失败。
- 收到可核验最终费用：以实际积分记账并释放未用预占；重复回执幂等。
- 传输断开、视频已受理但未完成、回执缺失或编号不匹配：保留预占，标记 `reconcile_required`；只查询，不自动重新提交。
- 明确最终费用为零：记录零额最终回执并释放预占，不以“没有金额字段”推断为零。
- 实际金额超过报价/预占：保存真实费用证据并标记上界违例，冻结该 Key 的后续付费请求并告警；不得把真实费用丢弃或伪装成成功结算。超过 Key 可用余额的差额单独呈现为账务缺口，待管理员处理。
- `stream=true`：保持同一请求编号，AI Work 将最终账单持久化；HTTP 流结束后 Core 查询最终回执。客户端断开不自动重发上游请求。
- 视频：202/任务受理只建立持有和任务关联；完成后查询任务级真实积分回执才结算。任务查询或下载本身不重复扣任务费。
- 客户端重试遵从现有幂等键语义；同一幂等操作不能建立第二笔预占或重复调用上游。

## 6. 积分与 Key 账本

### 6.1 核心定义

设 AI Work 最近一次成功核实的统一可用上游积分为 `U`，每个 Key 经增配/调整后的有效额度减去已核验实际扣费所得剩余额度为 `R_i`，尚未结算预占为 `H_i`：

- `Key 剩余余额 R_i = 已分配额度 - 已核验实际扣费`。
- `Key 可用余额 = R_i - H_i`。
- `Core 可分配积分 = max(0, U - ΣR_i)`。预占尚未结算，仍包含在所属 Key 的剩余额度 `R_i` 中，不重复扣除。
- 并发请求先以请求级报价检验并原子占用 Key 可用余额；两个 Key 的额度及持有记录不可互相抵销。

“积分池充值”不再作为管理员分配 Key 额度的前置步骤。管理员直接选择显示名称对应的 Key 增配；Core 先刷新 AI Work 上游余额，再原子检查可分配数并拒绝超额。刷新失败时不接受新增额度，并显示最近一次同步状态。

### 6.2 上游余额缺口

如果 AI Work 上游可用余额因 Core 外部消费或其他来源变化而低于 `ΣR_i`：

- 展示缺口数和上次刷新时间；
- 停止新增额度与新的付费请求；
- 保留各 Key 的账本与余额，不静默扣减、退款或重分配；
- 已在途请求按各自回执完成结算/对账。

上游聚合余额只用于总量校验和界面展示，不能参与某个 Key 的单次结算。

### 6.3 持久账本

Core 采用追加式记录，至少区分 `grant`、`reserve`、`settle`、`release`、`admin_adjustment` 和 `reconcile`。每条请求账目关联 `request_id` 与 `key_id`；唯一约束保证同一请求只有一次最终结算。管理员额度调整、Key 状态变化和明文复制操作写审计事件，但不记录 Key 明文。

## 7. Core 管理界面

### 7.1 独立概览页

- 独立展示上游当前可用积分、Key 未用额度总和、可分配积分、待结算预占、待对账数和已核验消耗。
- 积分消耗曲线按实际结算时间排序，只绘制已核验真实扣费；支持全部 Key 或单个 Key 过滤。
- 预占与待对账在曲线旁单独标识；不能把预占算作已消耗。
- 不展示活跃账号数。
- AI Work 桥接 URL、桥接密钥和其他运维设置放在设置区，不塞进概览页。

### 7.2 Key 管理列表

创建表单只需显示名称、最大并发数和能力勾选项；ID 自动生成，不需要先建用户。能力以中文复选框显示：文字处理、视频生成（含查询/下载）、素材上传。列表显示名称、脱敏 Key 标识、已分配额度、真实已用、剩余、预占、并发、能力和状态。

每条 Key 支持随时复制、追加额度、调整并发、启用/关闭、查看使用情况。分配额度时显示实时可分配数；金额超出时阻止保存并显示剩余数。文字与视频共用同一 Key 积分余额。旧测试 Key 不迁移，因此最终新环境不需要从旧哈希恢复 Key 明文。

### 7.3 Key 密文与复制安全

- 生成 Key 时仍保存认证用哈希，同时使用服务器端稳定的密钥管理材料加密保存可复制的密文，支持 Key 随时复制。
- 加密密钥不与密文放在同一个数据库字段或同一份数据库备份中；生产配置须持久化并具备版本标识。
- 管理员点击复制时通过鉴权接口按需解密，明文只短暂出现在授权的管理界面/剪贴板，不写入 localStorage、URL、日志、错误消息或统计接口。
- 复制与额度、并发、启停变更均写审计记录；列表默认只显示脱敏标识。

## 8. 稳定后干净切换

当前测试数据继续保留到改造及验收稳定，不提前删除。最终切换的 Core 数据边界为：

**不迁移并在新环境稳定后废弃**：测试用户映射、全部普通客户端 API Key、Key 额度、持有/结算账本、请求/回执记录、视频任务和使用统计。所有旧普通 Key 必须失效，不能仅从列表隐藏；新环境重新创建并签发全部普通 Key，旧账目不进入新图表。

**保留**：Core 管理员账户、AI Work 上游账户/凭据/真实积分、生成的视频与素材文件。Core—AI Work 桥接密钥在新环境切换时轮换并在两端更新。

删除旧数据只在新环境验收稳定后执行。届时必须先只读确认数据库/目录的精确路径、运行实例和影响范围，再按用户授权清理；本设计阶段及实现开发阶段不执行数据删除。

## 9. 错误处理与可观测性

- 无可用报价/最高扣费额：拒绝提交并返回可识别的额度/计费不可用错误。
- Key 余额或并发不足：Core 在上游调用前拒绝，不创建上游任务。
- 已确认上游拒绝：释放预占。
- 上游结果未知：保留预占，不重试、不声称已结算成功；后台可按同一请求编号查询/对账。
- 回执缺字段、错误单位、编号不匹配、精度超限或冲突：不结算，记录脱敏错误并待对账。
- 上游总额低于 Key 余额承诺：阻止新分配/付费提交并在概览告警。
- 日志只记录请求编号、Key 内部 ID、金额、状态、脱敏错误码和耗时，不记录 Key 明文、桥接密钥、Cookie、JWT、完整提示词或用户素材。

## 10. 测试与验收

### 自动化测试

1. 两个不同 Key 并发请求，各自持有和扣账不串；同 Key 并发预占原子化，不能超余额。
2. 正确回执按实际积分结算；重复相同回执不重复扣费；冲突回执进入待对账。
3. 预占后明确失败释放；成功回执释放差额；超上界费用记录真实缺口、冻结 Key 并告警。
4. 请求超时、AI Work 重启、Core 重启、视频任务延迟完成，均保持请求编号并可恢复查询，不自动重发。
5. 流式终态回执、非流式回执和视频任务回执均关联同一请求编号。
6. 缺少真实费用证据时不使用 Token、固定 1、duration 或聚合余额差完成结算。
7. 上游余额刷新失败、低于已分配余额、额度并发增加时，系统拒绝超额分配/付费操作。
8. Key 密文持久化可复制、哈希仍可认证、日志和列表脱敏；旧 schema/测试数据库按迁移策略处理。
9. 概览曲线只包含已核验结算，时间顺序正确，Key 筛选不混账；活跃账号数不展示。
10. 最终干净切换验证所有旧普通 Key 失效，所有新 Key 为新身份，AI Work 上游凭据与媒体文件未被误删。

所有本轮测试缓存、临时数据库、构建产物和验收文件放在 `D:\gpt` 下的专用目录，不在 C 盘堆积测试文件；用户数据和生产数据库不作为临时测试目录。

### 真实积分验收

只有回执生产和查询链路已部署、测试 Key 有真实可用额度、报价上界可信时，才进行一次最小真实请求。优先用现有“周”Key完成一次；不自动加额度、不重复发送。验收记录对照同一 `request_id` 下的 AI Work 回执与 Core Key 账本实际扣费。若回执或费用上界缺失，停止真实测试并维持付费请求的 fail-closed 状态，不把测试标记为通过。

按用户已授权的范围，不进行额外并发或重复真实付费测试；跨 Key 并发隔离由自动化测试验证。

## 11. 发布顺序与边界

1. 先实现与自动化验证新的回执契约、请求账本、预占/结算和 Key 分配约束。
2. 再更新独立概览页、曲线和 Key 管理列表。
3. 部署桥接和 Core 兼容版本；无法提供可信上界/回执的付费路径保持关闭或拒绝，不伪装兼容。
4. 完成一次受控真实积分验收并核对账本。
5. 稳定后按第 8 节切换新 Core 数据集、轮换桥接密钥、重新生成普通客户端 Key。数据清理另行进行目标确认。

部署到公网、切换生产数据集以及删除旧数据库/目录是不同的运维动作；本设计批准不等于立即授权执行这些动作。

## 12. 与既有设计的关系

本文整合逐请求真实积分结算与 Key 管理。对于“普通文字请求固定扣 1”“Key 积分需先经独立积分池充值”“Core 额度不以 AI Work 当前可用余额约束”等旧假设，以本文确认的规则为准。既有视频回执方案中“未核验不结算、未知保持持有、视频需可信上界”的安全要求继续有效。
