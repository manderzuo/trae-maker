# CORE 管理工作台界面改造规格

日期：2026-09-20  
状态：待确认  
范围：把现有 API 管理弹窗内的 Core 管理面板改造成独立、可持续操作的 Core 管理工作台。

## 1. 目标

CORE 是网关的管理与调度账本，不是普通模型编辑器。界面需要让管理员能够在一个独立工作区内完成：

- 查看 Core 运行状态、数据库状态和调度健康度；
- 管理用户和 Core API Key；
- 设置文字、视频、素材等资源的额度；
- 查看 Key 的总额度、已结算/已使用、占用和剩余额度；
- 查看脱敏的视频任务队列和异常租约；
- 执行 legacy 额度迁移；
- 明确看到 Core 当前是 off、shadow 还是 enforce 模式，以及哪些操作会影响真实请求。

界面不展示 API Key 明文、凭据、完整 prompt、本地结果路径或上游账号标识。管理员 Key 只存在当前内存会话中。

## 2. 现状与改造边界

当前 `CoreAdminPanel` 已具备大部分后端命令调用，但全部塞在 `ApiManagerModal` 的一个 tab 中，信息密度高、状态与操作混杂，且 Core 的关键概念不够明显。

本次改造：

- 新增独立 Core 管理工作区入口；
- 把状态、用户/Key、额度、任务与迁移拆成清晰的工作区页面/分区；
- 复用现有 Tauri Core 命令和数据结构，只有在验收发现数据不足时才增补最小后端 DTO/命令；
- 保留现有 API 管理弹窗的入口作为跳转入口或兼容入口，不让旧面板成为唯一管理入口；
- 不改变 Core 数据库、鉴权、额度结算和 fail-closed 规则。

## 3. 工作区结构

### 3.1 顶部状态栏

固定显示：

- Core 模式：关闭 / 观察 / 强制；
- 网关运行状态；
- schema 版本和数据库路径的脱敏/可复制显示；
- 外键是否启用；
- 调度健康摘要：账号、fresh/stale observation、活动 lease、unknown lease、槽位饱和、reader 失败；
- 手动刷新按钮；
- 当前管理员会话状态和“清除本次 Key”按钮。

模式为 `enforce` 时显示醒目的真实额度/真实请求提示；`shadow` 只能查看，不把管理操作误认为已接管真实流量。

### 3.2 左侧导航

独立工作区提供以下五个分区：

1. **总览**：健康卡片、额度概览、最近异常任务；
2. **用户与 API Key**：用户状态、角色、Key scope、启用/撤销和一次性签发明文；
3. **额度中心**：按资源类型查看并发、available、held、settled/已使用和总量，支持用户额度、Key 额度与 legacy 迁移；
4. **任务与租约**：视频持久队列、状态筛选、unknown/待对账告警；
5. **迁移与安全**：legacy 迁移检查、迁移执行、管理员会话安全提示和危险操作记录说明。

资源类型默认提供 `chat_request`、`video_job`、`asset` 三个选项，同时允许选择后端返回的其他资源类型，不在前端写死计费单位。

## 4. 核心交互

### 4.1 管理员会话

- 初次进入只显示状态和管理员 Key 输入区；
- Key 不写入 localStorage、配置文件、URL 或日志；
- 点击加载后并行获取用户、Key、调度状态和视频任务；
- 刷新失败保留上一次数据，同时在页面顶部显示错误，不清空已有状态；
- 离开工作区或点击清除时清除内存中的管理员 Key 和敏感响应状态。

### 4.2 用户与 Key

- 用户表显示 ID、名称、角色、状态和更新时间；
- 支持创建用户、启用/禁用用户；
- Key 表显示名称、归属用户、prefix、scope、状态、创建时间；
- 支持按用户筛选和撤销 Key；
- 签发 Key 时用 scope 多选，而不是要求管理员记忆逗号格式；至少提供 `chat:invoke`、`videos:submit`、`videos:read`、`assets:write`、`assets:read` 的可选项；
- 明文只在签发成功弹层中展示一次，关闭后只保留 prefix。

### 4.3 额度中心

额度卡片至少呈现：

```text
总量 = available + held + settled
剩余 = available
占用 = held
已使用/已结算 = settled
```

如果后端返回迁移状态或未配置标记，显示状态徽标：ready、legacy_unassigned、reconcile_required 等。不能把 `held` 合并到已使用，也不能把 `0` 显示成“无限”。

管理员操作需要二次确认：

- 向用户发放额度；
- 向单个 Key 发放固定额度；
- 执行 legacy 额度迁移；
- 未来如新增扣减/冻结操作，同样必须确认并填写原因。

每次操作显示资源类型、数量、对象、原因，成功后自动刷新对应余额。

### 4.4 任务与租约

视频任务列表只显示当前 Core 管理 DTO 已允许的脱敏字段：任务 ID、用户、模型、状态、额度状态、尝试/lease 状态、更新时间和待对账标记。

任务状态使用稳定色彩：

- queued：中性；
- running：蓝色；
- succeeded/canceled：绿色；
- unknown/cancel_requested/reconcile_required：琥珀色；
- failed：红色。

对 unknown 或待对账任务显示“额度仍被保留，不能从管理界面自动重放”的警告，不提供可能造成重复扣费的重放按钮。

### 4.5 迁移与安全

- 先执行只读 migration inspect，显示可迁移条目、缺失映射和冲突；
- 只有检查结果可执行时才显示应用按钮；
- 执行需要管理员确认、迁移映射和 migration ID；
- 迁移完成后自动刷新用户、Key 和额度；
- 迁移与撤销等不可逆操作使用明确的危险样式和文字确认。

## 5. 与 Seedance Chat 兼容改造的关系

Core 工作台是管理面，不承担 Chat Completions 到 Seedance 的协议投影。两者通过以下数据边界连接：

- Seedance Chat 适配器使用 Core 的 `videos:submit` scope；
- 视频额度使用 `video_job` 资源账本；
- 任务与租约结果通过任务与租约分区查看；
- 管理员在额度中心给用户或 Key 配置可消耗额度；
- 普通文字请求仍使用 `chat:invoke` 和 `chat_request` 账本。

## 6. 验收标准

1. 不打开旧的大型 API 管理弹窗也能进入 Core 工作台；
2. 页面首次进入不会自动填充或持久化管理员 Key；
3. 状态、调度健康度、用户、Key、额度和视频任务可分别刷新；
4. 刷新失败不丢失已显示数据，并提供明确错误；
5. 用户创建、启用/禁用、Key 签发/撤销均有确认和成功反馈；
6. Key scope 使用可读的多选控件，提交值与 Core 后端 scope 一致；
7. Key 明文只展示一次，任何列表、错误和日志都不显示明文；
8. 额度中心明确区分总量、剩余、占用和已结算，资源类型切换不串数据；
9. 发放、迁移等操作必须填写原因并二次确认；
10. unknown/待对账任务不提供自动重放；
11. 迁移检查与执行严格按管理员鉴权和后端返回状态显示；
12. `npm test`、`npm run build` 和 UI 按钮检查通过；
13. 不改变 Core 后端鉴权、额度结算、真实积分和 fail-closed 语义。

## 7. 明确不做

- 不在 UI 中展示真实 API Key、上游账号凭据或完整视频输入；
- 不把 Core 管理界面改成普通模型配置页面；
- 不提供自动重放 unknown 视频任务；
- 不让前端绕过 Core 命令直接读写 SQLite；
- 不因 UI 改造自动切换 Core 模式或重启生产网关。
