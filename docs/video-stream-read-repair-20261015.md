# 视频读流恢复边界与诊断补全（2026-10-15）

回归排查确认，10 月 12 日将 `lines().flatten()` 改成第一次读取错误即退出后，会提前结束仍可继续读取的临时错误；旧循环又可能在持续错误时无限循环。最新一次真实故障只保存了 `video_stream_read_failed`，未保留底层 IO 原因，所以不能断言真实故障就是可恢复错误，也不能把它直接归因于上游。最近成功版本与当前版本的视频提交、协议、读流和依赖文件一致，实际单图 5 秒 / 480p / 9:16 请求字段也与历史成功样本一致。

## 修复行为

- 视频生成 POST 与其响应体使用同一 1800 秒 deadline，心跳和读取恢复均不延长期限；文字模型通道不变。
- 仅 Interrupted、TimedOut、WouldBlock 及明确包裹这些 IO 类型的 Other，在原响应 reader 上最多合计恢复一次。保留半行字节、UTF-8 边界和已解析事件，不能重放已消费事件。不是重新联网或重新生成，未新增 POST、预算、账号切换或收费重试。
- 连接重置、UnexpectedEof、InvalidData、未知 Other、非法分块/事件及超长事件仍停止，保存 unknown。单事件 1 MiB 上限也覆盖恢复前后的累计数据；已确认终态仍立即结束，不能读取后续错误覆盖它。
- 诊断附带闭合元数据：最后 IO 类型、最多八层 IO 原因类型、系统错误码、读取恢复次数、已消费字节/事件数、读流耗时、是否触及 deadline、HTTP 状态和归一内容类型。未保存原错误消息、地址、响应头、提示词、密钥或签名 URL；ureq 自动解压后不暴露原 Content-Encoding，因此不虚构压缩类型。
- 新元数据为可选字段，旧诊断的 JSON 形状与摘要验证保持兼容。诊断仍不是费用回执；原 request/task/account/session/budget、真实账单、unknown 的持有及迟到结果规则不变，无数据库迁移。
