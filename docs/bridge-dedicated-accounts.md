# Core 专用账号的容量核对

本功能将“每个 Key 的实际扣费结算”和“上游账号可再次授权的容量”分开：回执确认后先进入持久 outbox；账号整体容量随后在空闲窗口核对。原始费用记录始终保留。

## 启用前提

管理员明确保证名单中的上游账号只经 Core 使用，不在官方客户端、其他代理或脚本中消费。这是运维约束，不是上游提供了最终账单标记。先用只读及受控实测验证真实积分包响应，再启用生产配置。

在 AI Work **数据根目录**（与桥接数据库同层，而不是其 `data` 子目录）放置：

```json
{"version":1,"accounts":["实际确认专用的账号UID"]}
```

文件名为 `bridge-dedicated-accounts.json`。没有文件或名单为空时不开启；不支持通配符。最多256个不同账号，文件最多32KiB。该文件不是凭据，不填写 API Key/JWT，也不能从公网请求提交。移除某个账号即停止后续自动容量核对，旧费用和占用不会被删除。

初次新建容量记录时，积分包基线与容量在同一事务写入。对于已存在但没有基线、存在旧版会话或未知费用的账号，不自动认定历史已对清；需要先完成专门迁移核验。不要删库、清占用或用当前余额覆盖历史事实。

## 核对条件

1. 账号没有准备中、执行中、待回执或冲突费用；执行已终态且单请求回执符合既定唯一会话的完成后读取政策。
2. 在持久账号栅栏期间读取权益包；网络不持数据库或全局 runtime 锁。
3. 旧包仍可匹配，限额/生效期未变化，用量没有下降；新增包的已有用量也计入增量。
4. 全部包用量增量，精确到百万分之一积分，等于本地尚未覆盖的实际扣费合计。
5. 提交时实例、栅栏、快照、账单事件和旧会话水位未变化。

新容量、覆盖事实、新基线同事务提交；失败全部回滚。缺失包（包括上游不再返回的过期包）、退款、未知积分产品、重复包、上游字段不稳定或不一致的实际扣费，都不能凭猜测覆盖。该情况下仍保留财务事实，并需要进一步核验；不是永久保证任意历史余额都能自动恢复。

当前支持通用积分产品208、每月登录积分221、Work积分产品209。真实只读响应已确认稳定身份字段为 `entitlement_base_info.entitlement_id`；优先使用其摘要，其次支持显式 `id`，均不落库原始账号信息；缺少身份字段时要求完整非 `usage` 内容保持稳定，变化时保守拒绝。

真实响应中签到积分包可能为 `usage: {}`。此类包不再使整个账号解析失败，但因缺乏精确已用数，暂不计入预算可授权容量（不影响原有展示余额）；以后出现明确用量时，将其全部已用数纳入新包差额核对。`usage: null` 或格式损坏仍拒绝。不能将空对象擅自视为已用0，因此预算可用容量可能低于桌面展示余额。该差异需在真实付费验收中继续校准。

本轮对一个真实账号做过连续两次只读查询：支持上述真实包结构，零变化匹配。此结果证明读取及稳定身份可用，不是实际付费后账单覆盖证明。

## 运行与边界

- 已完成回执但尚未核对容量的账号仍进入现有后台刷新队列；重启可重新发现。复用4个worker及已有退避，不创建每请求新线程，不再次生成视频。
- 仅在有相关工作时查询，不周期性扫描所有账号。准备新请求发现新增积分包/容量增长时，可触发一次栅栏内重读，核对零费用增量后更新容量。
- 桥接权益查询15秒总超时。单 Key 账单/额度释放不等待账号整体容量核对；但被核对账号短时不接新预算，其他账号仍可工作。
- 此功能不提供跨账号分摊，不把池外消费计入某个 Key，不放行未知价格，也不冻结整个 Key 余额。
- schema7只新增独立基线表并原子迁移。旧schema6程序不能直接打开升级后的数据库。生产升级前须做一致性备份和副本迁移验证；有新交易后不能覆盖回旧备份来“回滚”。

隔离测试使用合成权益包及真实本地事务，并非上游官方账单、真实下载或公网验收证据。
